# Al-Hidayah V2: MongoDB plan

**Status:** proposed for V2, not implemented. **Date:** 2026-11-19.

The owner requested MongoDB for a later version if a database became useful. V1 remains a static, account-free application: reminders come from verified build-time JSON, and favorites and settings stay on the visitor's device. No database credentials, database driver, reviewer API, or remote favorite sync belong in V1.

## 1. Why V2 may need MongoDB

A database becomes useful for work that a static site cannot safely perform:

- reviewer accounts and role-based access;
- human approval records for reminders and category assignments;
- immutable publication and audit history;
- optional, explicit favorite synchronization across a visitor's devices;
- operational reporting that does not track visitors or build advertising profiles.

MongoDB is a fit because review records and publication manifests are document-shaped, may evolve independently, and benefit from transactional updates. It does not replace the frozen source datasets or make scripture freely editable.

## 2. Architecture

```text
Cloudflare Pages                 secured Node.js API                MongoDB Atlas
Static V1/V2 client  ---------->  authentication + RBAC  ---------->  private database
Public read-only JSON            validation + audit log              least-privilege user
                                  publication service
                                           |
                                           v
                              validated, versioned public snapshot
```

- Keep the static site on Cloudflare Pages.
- Use a small Node.js service on a host that supports the official MongoDB Node.js driver and outbound TLS connections. Do not assume a Cloudflare Worker can open a MongoDB TCP connection.
- Use MongoDB Atlas with a least-privilege database user, TLS, network allow-listing, encrypted backups, and secrets supplied only by the server environment.
- The browser never receives the MongoDB connection string or talks directly to Atlas.
- Public visitors continue reading static snapshots. A database outage must not make the public reminders unavailable.
- Reassess free-tier limits before implementation. V2 has no approval for paid infrastructure by default.

## 3. What MongoDB must not store as editable content

MongoDB is not an open text editor for the Qur'an or Hadith.

- Arabic, translations, grading, and references still originate from pinned, validated datasets.
- A review record points to an `itemId` and the exact dataset checksum. It does not silently replace source text.
- Any source-text correction follows the existing separate data pull request, checksum update, and named-reviewer process.
- Category names, suitability decisions, translations, and grading are never generated by the API or an AI agent.
- A publication is valid only when every referenced item passes the same structural and integrity checks used by the static build.

## 4. Proposed collections

### `users`

Reviewer and administrator accounts; ordinary visitors do not need accounts.

```text
_id, email, normalizedEmail, displayName, role, status,
credentialVersion, createdAt, updatedAt, lastLoginAt
```

- `role`: `reviewer` or `admin`.
- Unique index on `normalizedEmail`; index on `role, status`.
- Store authentication secrets only as password hashes or refresh-token hashes, never plaintext tokens.
- Logs use the user id and action, not full email addresses.

### `reviewDecisions`

The human decision about one exact dataset record.

```text
_id, itemId, datasetChecksum, decision, reviewedCategories,
reviewerId, notes, createdAt, supersededBy
```

- `decision`: `approved`, `rejected`, or `needs_context`.
- Compound index on `itemId, datasetChecksum, createdAt`.
- A checksum change invalidates earlier approval automatically.
- Decisions are append-only; correction creates a superseding record.

### `poolPublications`

An immutable, reproducible snapshot approved for the public build.

```text
_id, version, sourceManifest, itemIds, categoryAssignments,
reviewDecisionIds, publishedBy, publishedAt, snapshotSha256
```

- Unique index on `version` and unique index on `snapshotSha256`.
- `sourceManifest` contains source identifiers and checksums, not rewritten scripture.
- Publishing verifies that every item has an eligible decision for the same checksum.
- A new publication never mutates an earlier one.

### `favoriteSync` — optional and off by default

```text
_id, userId, itemId, savedAt, updatedAt, deviceLabel
```

- Unique compound index on `userId, itemId`; index on `userId, updatedAt`.
- Requires an explicit visitor choice and a clear privacy explanation.
- V1 local favorites remain usable without registration.
- Synced favorites contain no notes, location, prayer history, or behavioral profile.

### `auditEvents`

```text
_id, actorId, action, targetType, targetId, requestId,
metadata, createdAt
```

- Index on `actorId, createdAt` and `targetType, targetId, createdAt`.
- Record sign-in failures, role changes, review decisions, publication, export, and deletion.
- Never record passwords, tokens, full email addresses, or scripture as an editable diff.
- Define an owner-approved retention period before launch.

## 5. API boundaries

Every protected route passes through authentication and then an explicit `requireRole(...)` check. Hiding a button is not authorization.

```text
POST   /auth/sign-in
POST   /auth/refresh
POST   /auth/sign-out
GET    /review/items?status=needs_context
POST   /review/decisions
GET    /review/publications
POST   /review/publications
GET    /sync/favorites
PUT    /sync/favorites/:itemId
DELETE /sync/favorites/:itemId
DELETE /sync/favorites
```

- Validate every request body, parameter, content type, and payload size at the API boundary.
- Apply rate limits to authentication and write endpoints.
- Use short-lived access tokens, rotated refresh tokens, secure cookie settings where cookies are used, and CSRF protection for cookie-authenticated writes.
- Return generic authentication errors; keep detailed validation errors free of sensitive values.
- Add authorization tests before handlers, including the proof that a reviewer cannot perform admin actions.
- Publication uses a transaction so an incomplete manifest cannot become visible.

## 6. Migration from V1

1. Release 1.0 and its human review gate are complete before V2 begins.
2. Deploy the API with no public write access and prove least-privilege roles in staging.
3. Import existing reviewed pool manifests by reference and checksum, not by rewriting religious text.
4. Run the same validation against every proposed publication; compare the generated snapshot byte-for-byte with the approved V1 pool.
5. Keep favorite sync disabled initially. If enabled later, let a signed-in visitor explicitly upload the existing V1 JSON export.
6. Validate imports, deduplicate by item id, and never clear local favorites after upload without a separate confirmation.
7. Keep a static rollback snapshot available throughout migration.

## 7. Backup, privacy, and recovery

- Enable Atlas backups and test a restore before reviewer accounts are opened.
- Keep database and API regions consistent with the owner's privacy decision.
- Collect only account, review, publication, and explicitly synchronized favorite data.
- Do not add analytics, advertising identifiers, precise location storage, or prayer-history tracking.
- Provide account deletion and favorite-sync deletion paths.
- Document retention for audit events and deleted-account backups.
- A failed publication leaves the last valid static snapshot untouched.

## 8. Delivery sequence

| Gate | Deliverable | Acceptance condition |
|---|---|---|
| V2.0 | Owner decisions | Hosting, account necessity, retention, regions, and reviewer roles approved |
| V2.1 | Threat model and schemas | Security review covers every collection and route |
| V2.2 | Authentication and RBAC | Wrong-role and unauthenticated tests fail closed |
| V2.3 | Review workflow | Checksum-mismatched approvals cannot publish |
| V2.4 | Static publication | Snapshot reproduces the reviewed pool and passes all V1 checks |
| V2.5 | Optional sync | Explicit consent, import/export round trip, deletion, and offline behavior verified |
| V2.6 | Recovery and release | Backup restore, outage fallback, accessibility, and human content review signed off |

## 9. Decisions still owned by the project owner

- Whether cross-device favorite sync justifies visitor accounts at all.
- Who may be a reviewer and who may publish.
- API hosting, Atlas region, retention periods, and any future paid tier.
- The exact reviewer workflow for context, categories, translations, and grading.

Until those decisions and Release 1.0 are complete, this document is a design boundary only. V1 stays static and local-first.
